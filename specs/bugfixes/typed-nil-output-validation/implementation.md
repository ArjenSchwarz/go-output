# Implementation Explanation: Typed-Nil Output Validation (T-1649)

Branch: `T-1649/bugfix-typed-nil-output-validation` vs `origin/main`
Generated by pre-push review.

## Beginner Level

### What Changed

The go-output library lets you build an `Output` by handing it building
blocks: renderers (turn a document into JSON, a table, etc.), transformers
(modify the rendered bytes), writers (send the bytes somewhere), and a
progress indicator. Before this fix, the library checked that you didn't
hand it "nothing" (`nil`) — but the check could be tricked.

In Go, an interface value is a small box holding two things: *what type* the
value is and *the value itself*. If you put a nil pointer into that box, the
box itself is not empty — it says "this is a `*FormatAwareTransformer`...
that happens to be nil". A check like `value == nil` looks only at whether
the box is empty, so this "typed nil" sneaks past. Later, when the library
tries to actually use the value, the program crashes with a nil-pointer
panic.

The fix adds one small helper, `isNilValue`, that opens the box (using Go's
reflection feature) and checks whether the value inside is nil. Every place
that validated options now uses this helper.

### Why It Matters

It is easy to create a typed nil by accident: `NewFormatAwareTransformer(nil)`
returns a nil pointer, and passing that to `WithTransformer(...)` boxes it
silently. Before, that mistake crashed your program mid-render with a
confusing panic message. Now you either get a clear validation error telling
you exactly which option was nil, or the nil value is safely ignored where
that was already the documented behavior.

### Key Concepts

- **Interface**: a Go type that says "anything with these methods". Think of
  it as a labeled box: label (type) + contents (value).
- **Typed nil**: a box with a label but nil contents. The box is not empty,
  so `== nil` says "not nil" — but using the contents crashes.
- **Reflection**: Go's ability to inspect a value's type and contents at
  runtime; `reflect.ValueOf(x).IsNil()` can see through the box.
- **Panic vs error**: a panic is a crash; an error is a value you can check
  and handle. This fix converts crashes into errors (or safe no-ops).

## Intermediate Level

### Changes Overview

Three commits plus a review-round doc commit:

1. `v2/errors.go` — new unexported helper `isNilValue(value any) bool`:
   returns true for untyped nil and for nil values of the nilable reflect
   kinds (Pointer, Map, Slice, Func, Chan, UnsafePointer; the Interface arm
   is unreachable via an `any` parameter and kept as future-proofing).
   `ValidateNonNil` now delegates to it.
2. Applied at every Output validation point:
   - `validateConfigEntries` (`v2/output.go`) — typed-nil renderers,
     transformers, and writers now fail `Render` with the documented
     `*ValidationError`, including the slice index (`transformers[0]`).
   - `NewOutput` progress fallback — a typed-nil `Progress` is treated as
     absent and replaced with the no-op progress.
   - `TransformPipeline.Add` (`v2/transformer.go`) — ignores typed nils like
     it already ignored untyped nil.
   - `NewFormatAwareTransformer` (`v2/format_aware.go`) — returns nil for a
     typed-nil inner transformer.
   - `StdoutWriter.SetWriter` / `StderrWriter.SetWriter` — ignore typed-nil
     `io.Writer` values (completes the T-1387 deferral).
   - `MultiWriter` (`v2/multi_writer.go`) — `NewMultiWriter`/`AddWriter`
     drop typed-nil writers; the defence-in-depth skip in the `Write` loop
     is typed-nil aware too (added in a review round).
   - `Render(ctx, nil)` — a nil `*Document` boxed into `any` by
     `ValidateNonNil("document", doc)` is now caught.
3. `v2/typed_nil_validation_test.go` — nine regression tests covering every
   application point, with purpose-built stub types whose pointer-receiver
   methods touch fields so any nil dereference is guaranteed to panic.

### Implementation Approach

One shared helper applied at the *existing* guards — no new validation
layer. The error-vs-ignore split is not new policy: each site's typed-nil
handling mirrors its pre-existing untyped-nil handling. Where untyped nil
already produced a validation error (`validateConfigEntries`,
`ValidateNonNil`), typed nil now errors; where untyped nil was already
silently ignored (progress default, pipeline `Add`, `SetWriter`,
`MultiWriter`), typed nil is ignored the same way.

### Trade-offs

- **Validate at Render, not in `WithX` options**: functional options have no
  error return, so construction-time rejection would mean silent drops or
  panics. Render-time validation keeps the documented error path and reports
  the exact index.
- **Reflection cost**: ~2 ns per check, zero allocations (the
  `reflect.Value` does not escape). Negligible against per-render goroutine
  spawns and I/O.
- **`ValidateNonNil` is exported**: its semantics change is a deliberate
  public API behavior change, documented in the godoc and CHANGELOG — e.g.
  `ValidateNonNil("x", []int(nil))` now errors where it previously passed.

## Expert Level

### Technical Deep Dive

`isNilValue` handles the full set of nilable kinds. Empirical verification
during review confirmed: `reflect.Value.IsNil` accepts `UnsafePointer`
(the implementation's switch is `Chan, Func, Map, Pointer, UnsafePointer`
plus `Interface, Slice`), so no panic path exists through the helper; a nil
`error` assigned to `any` flattens to untyped nil (caught by the early
return); a typed-nil `error` re-boxed into `any` presents its dynamic kind
(`Pointer`), never `Interface` — hence the Interface arm being dead code by
construction for an `any` parameter.

The MultiWriter `Write`-loop check is the only post-construction guard and
is unreachable in the current code (constructor and `AddWriter` are the only
entry points into `mw.writers`), retained as defence in depth against future
mutation paths. It costs ~0.3 ns per writer per Write against a goroutine
spawn per writer.

Concurrency: no new locks. `validateConfigEntries` validates the same
snapshot (copied under `o.mu.RLock`) that `renderWithConfig` consumes, so
there is no TOCTOU window; `MultiWriter.Write` checks its own snapshot.

### Architecture Impact

The helper gives the package a single point of truth for interface nil-ness,
positioned next to the other `Validate*` helpers. Prior art
(`isHashableError`, the `sealContents` typed-nil walk) has different
semantics and correctly remains separate. Prevention guidance in the bugfix
report directs future validation of interface-typed config values through
`isNilValue`.

### Potential Issues

- A pathological-but-legal implementation whose methods are nil-receiver
  safe (e.g. value methods on a nil map type) previously rendered
  successfully and is now rejected or ignored. Inherent to typed-nil
  rejection; matches ticket intent.
- Same-bug-class sites outside this ticket's Output-option scope remain:
  renderer `RenderTo(w io.Writer)` guards use `w == nil` (public entry
  point bypassing Output validation), `Builder.AddContent`/
  `SectionContent.AddContent` accept typed-nil `Content` (defended
  downstream by `sealContents` but with `== nil` skips elsewhere),
  `Operation` filters (`WithTransformations`), `WithProgressWriter`, and
  `S3Writer`'s client check. Candidates for follow-up tickets, not this PR.
- Internal transformer-pipeline guards (`Remove`, `Has`, `sortTransformers`,
  `Transform`) still use `t == nil`; unreachable given `Add` is the only
  append path — cosmetic asymmetry with the upgraded MultiWriter loop guard.

## Completeness Assessment

**Fully implemented:** every validation point named by the consolidated
ticket (transformers per T-1649, progress per T-1654, renderers/writers per
T-1710, stdio SetWriter per the T-1387 deferral) plus MultiWriter from the
review round; regression tests for all of them; CHANGELOG and bugfix report
updated (report's MultiWriter omission fixed during this review).

**Partially implemented:** nothing within the ticket's scope.

**Missing (deliberately out of scope):** the adjacent `== nil` sites listed
under Potential Issues — same bug class, different API surfaces
(`RenderTo`, document content, operations, `WithProgressWriter`,
`S3Writer`). No requirement in the ticket or report covers them; they were
surfaced by this review for follow-up.
