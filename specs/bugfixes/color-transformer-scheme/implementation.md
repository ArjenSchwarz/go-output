# Implementation Explanation: ColorTransformer Honors Its ColorScheme (T-1518)

Generated by the pre-push review for branch `T-1518/bugfix-color-transformer-scheme`.

## Beginner Level

### What Changed

The go-output library can decorate terminal tables with colors: lines that
look like successes turn green, failures turn red, and so on. Users can pass
their own color choices in a `ColorScheme` (for example "make successes cyan
instead of green"). Before this fix, those choices were thrown away — the code
always used hard-coded green, red, and blue. Worse, if any part of the output
contained a success marker like ✅, the ENTIRE document was painted that one
color, including the failure rows.

Now the transformer reads the user's scheme and colors one line at a time.
A line with ✅ gets the scheme's Success color, a line with ❌ gets the Error
color, warning markers (🚨 or `!!`) get the Warning color, and ℹ️ gets the
Info color. Lines without any marker stay uncolored.

### Why It Matters

The whole point of coloring status output is to make failures stand out. When
one success marker turned the entire table green, a failing row looked exactly
like a passing one — the feature actively hid problems. And a user who
configured custom colors got silently ignored, which erodes trust in the API.

### Key Concepts

- **ANSI color codes**: invisible character sequences (like `\x1b[32m`) that
  terminals interpret as "switch to green". Coloring text means wrapping it
  in these sequences.
- **Transformer**: a small component that rewrites rendered output bytes
  before they are shown — think of a filter in a photo app.
- **Word boundary**: a regex trick (`\b`) that makes "No" match only the
  standalone word "No", not the "No" inside "Notes". Without it, ordinary
  text triggered coloring by accident.

## Intermediate Level

### Changes Overview

- `v2/transformers.go` — `ColorTransformer.Transform` rewritten: splits input
  on `\n`, applies `colorizeLine` per line, rejoins. Three new package-level
  declarations: `colorSchemeAttributes` (name → `color.Attribute` map for the
  8 ANSI colors, case-insensitive lookup), four compiled indicator regexes
  (`successIndicatorPattern` etc.), and `applySchemeColor` (lookup + optional
  bold + `Sprint`). `RemoveColorsTransformer`'s ANSI-strip regex hoisted to a
  package-level `ansiEscapePattern`.
- `v2/format_aware.go` — comment-only: cross-reference on
  `enhancedEmojiReplacements` pointing at the sibling indicator tables.
- `v2/transformers_color_test.go` — new regression tests (six test functions)
  that failed against the old implementation.
- `CHANGELOG.md` — Unreleased/Fixed entry flagging the rendered-byte changes.

### Implementation Approach

Per-line granularity mirrors the line-based processing already used by
`SortTransformer` and `LineSplitTransformer` in the same file. The scheme is
consulted at color-application time through a fixed name map, which keeps the
exported string-based `ColorScheme` API unchanged. `EnhancedColorTransformer`
(`v2/format_aware.go`) delegates to the same `Transform` and inherits the fix
without modification. Precedence when one line contains several indicator
roles is explicit and test-locked: success > error > warning > info; the
whole line takes the winning role's color. Success/error/warning lines render
bold, info lines plain — matching the original weights.

### Trade-offs

- **Per-line vs per-cell**: per-cell coloring would need to parse rendered
  table borders for every output style — fragile and much more code. Per-line
  already restores row-level signal.
- **Unknown color names leave text unstyled** rather than falling back to a
  default: a typo in a scheme becomes visible instead of silently producing
  default colors (the very defect being fixed).
- **Warning color change**: warnings now use the scheme's Warning (default
  yellow) instead of hard-coded red. This changes bytes but matches the
  documented intent of the scheme.
- **`OK` is not a color indicator**: the emoji tables convert `OK` → ✅, but
  the color patterns deliberately exclude it (too common in prose to justify
  coloring a whole line). Documented in cross-referencing comments on all
  three indicator tables.

## Expert Level

### Technical Deep Dive

- `strings.Split`/`strings.Join` on `"\n"` is a lossless round-trip,
  including trailing-newline and empty-input cases, so non-matching documents
  pass through byte-for-byte.
- The four indicator regexes and the name map are package-level `var`s —
  compiled/allocated once, read-only after init, so there is no mutable
  package state and no synchronization concern despite concurrent renders.
- `applySchemeColor` constructs a `color.New(attr)` per matching line. Only
  matching lines pay that cost; non-matching lines are a regex scan only.
  The fatih/color `Sprint` path respects the global `color.NoColor`, so
  behavior under non-TTY output is unchanged from the old implementation.
- Go's `regexp` `\b` is ASCII-aware, which is exactly right here: `\bYes\b`
  refuses to match inside "Yesterday" but matches "Yes" adjacent to table
  pipes, spaces, or punctuation. The emoji alternates (✅, ❌, 🚨, ℹ️) are
  matched as literals; ℹ️ is matched with its VS16 variation selector,
  consistent with how the library's own emoji transformer emits it.
- `RemoveColorsTransformer` previously recompiled
  `\x1B\[([0-9]{1,3}(;[0-9]{1,3})*)?[mGK]` on every call; the hoisted
  `ansiEscapePattern` is now the sole copy of that pattern in the package.

### Architecture Impact

The fix is confined to one transformer plus comments; no exported API
changed. The rendered bytes DO change wherever an indicator matched, which
is a behavioral break for anyone snapshot-testing colored table output —
hence the prominent CHANGELOG entry. The indicator word lists now exist in
three tables (emoji, enhanced-emoji, color) with keep-in-sync comments;
deriving all three from a single source of truth is a known deferred
follow-up.

### Potential Issues

- A line containing both ✅ and ❌ renders entirely in the Success color by
  precedence. For row-per-status tables this is correct; for dense
  single-line summaries it can understate failures. Test-locked as
  intentional.
- `ℹ` without VS16 does not trigger Info coloring. Acceptable: the library's
  own emoji pipeline emits ℹ️ with VS16.
- `!!` inside prose (e.g. "Really!!") colors the line as a warning; `!!` has
  no word-boundary equivalent. Same behavior class as the emoji transformer.
